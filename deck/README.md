# Deck v2.7 — 全セッション自動収集ウォッチャー

Claude Code の全セッション transcript（`~/.claude/projects/<エンコード済みパス>/<session-id>.jsonl`）を
常駐監視し、today-board（`C:\Users\<you>\.claude\today-board\board.html`）の
`<!-- DECK:AUTO:START -->` 〜 `<!-- DECK:AUTO:END -->` マーカー間に
「全セッションのカード」（状態と、TaskCreate 系か計画一覧があれば進捗）を自動挿入する。

- Python 3 標準ライブラリのみ（pip 依存ゼロ・単一ファイル `deck_watcher.py`）
- **外部ネットワーク通信なし。127.0.0.1 限定の受信ポート 1 つのみ**
  （ボードD&D移動の反映・通知音の設定と試聴・時刻上書きの中継・未確認通知の受け渡し。
  送信なし・v1.6 / v1.7）。ポートは **8737〜8746 のうち空いている最初の 1 つ**で、
  **起動ごとのトークンが無い・違う要求と、自分が監視している board.html を申告していない
  要求は断る**（v2.1・下記「受信ポートと照合（v2.1）」。トークンを知りうるものは同節の「限界」）。`projects/` は読み取り専用
- 書き換えるのは **board.html のマーカー間 ＋ ユーザーD&D移動の反映 ＋ 手書きセクションの
  完了表示の整合 ＋ 日付の切り替え ＋ ヘッダの値の計算し直し ＋ 欠けたマーカーの足し直し** の6つ。
  D&D 移動は手書き3セクション間の item ブロック再配置と進捗行の
  再計算のみ（v1.6）。完了表示の整合は状態チップを唯一の真実として `class` の
  `done-item` / `strike` トークンを足し引きするだけで、**チップ・タスクのテキスト・順序・
  セクション所属は変えない**（v1.8）。日付の切り替えは、日付の古いボードを退避して今日のボードを作る
  （済の行を除き、時刻付きの未完了を今日中へ移し、ルーチンの済を未に戻す＝下記「日付の切り替え（v2.2）」）。
  ヘッダの値は進捗（N / M とバー幅）・`<title>` の日付・`#upd-time`（v2.2）と、`<div class="board">` の
  `data-tb-rolled` / `data-tb-rolled-fp`（手書き部分が Deck 以外の書き手で変わったら外す・v2.3）。マーカーの足し直しは
  2つとも無い板に限り、Deck が書いた部分が空行だけを挟んでひと続きに残っていればそれを囲み、間に別の行があれば足さない（v2.5）。
  Deck が書いた部分が1つも無ければ、`<footer>` が1つだけの板でその直前に足す（v2.2）。**タスクの文言はどれも書き換えない**
- **時刻トリガーの通知音を鳴らす**（v1.7）。board.html を読んで予定時刻を判定し、
  `winsound`（Python 標準ライブラリ・**Windows 専用**）で鳴らす。
  非 Windows では音を鳴らさずに他の機能はそのまま動く
- `deck/` 配下に書くのは `state.json`・`sound.json`（`--board` で既定以外のボードを指したときはボードと同じフォルダ・v2.7）・`watcher.log` のみ
  （多重起動ガードのロックだけは **board.html ごと**に一時ディレクトリへ置く・v1.9）。
  `deck/` の外では board.html のほか、board.html と同じフォルダの `history/`（日付の切り替えで退避した
  元のボードと、形が崩れたときに退避した崩れる前の版〔v2.4〕）・`.guard/`（書き込みの記録と `format.json`〔v2.6〕）・`state.json`（`date` だけ）・`board.css` / `board.js` / `cat.png`（スキルの `assets/` と中身が違う
  ものだけ。常駐の起動時と5分ごと〔v2.3〕、および日付の切り替えのとき〔v2.2〕）に書く

## 起動

**通常はリポジトリ直下の `setup.bat` が配置・スタートアップ登録・起動まで行う**ので、
この節の操作は手動で動かしたいときだけ使う（`setup.bat` はスタートアップフォルダに
`today-board-deck.lnk` を作り、そのショートカットを `explorer.exe` で開いて起動する。
`pythonw deck_watcher.py` を直接は起動しない＝下記「ほかのプログラムから起動するとき」）。

`start-deck.bat` をダブルクリック。`pythonw` でコンソール非表示のまま常駐する。
（ダブルクリックで使うためのもの。Claude Code などのプログラムからは使わない＝下記）

- 多重起動ガード: **監視対象の board.html ごと**のファイルロックで単一インスタンスを
  保証する（v1.9・**常駐監視モードのみ**。`--once` はロックを取らない）。ロックファイル名は
  board.html の絶対パス（`realpath` + `normcase` で正規化）の SHA-1 から決め、
  `%TEMP%\today-board-deck-locks\deck-<16桁>.lock` に置く。ロックは**スクリプトの置き場所に
  依存しない**（成立条件＝**2 本が同じ一時ディレクトリを解決すること**。`TEMP` / `TMP` が
  異なる起動コンテキスト——別ユーザー・タスクスケジューラ・環境変数を上書きしたシェル——
  では別のロックになるためガードは効かない）
  - **同じ board を見る 2 本目は、置き場所が違っても起動しない**。`deck_watcher.py` の
    コピーが 2 箇所にあっても同じロックを奪い合う（v1.8 以前はロックが `deck/` の隣に
    あったため、コピーが 2 箇所にあると両方が常駐でき、同じ board.html を奪い合った）
  - 2 個目は即終了し、`watcher.log`（2 本目自身のフォルダ）と標準エラー出力に**稼働中の
    1 本目の PID・board・スクリプト位置・ログ位置・起動時刻**が出る（`pythonw` 起動では
    標準エラーは表示されないので、実質 `watcher.log` で確認する）
  - **違う board を見る 2 本は共存できる**。`--board` で別のボードを指したテスト実行は
    本番の常駐を妨げない。受信ポートは 2 本がそれぞれ別のものを取り（8737 が使用中なら
    8738、…）、どちらも自分のボードからの D&D 反映・通知音の設定を受けられる（v2.1。
    v2.0 までは 8737 を先に取った 1 本だけが受けられた）。確かめたのは同じ Windows ユーザーの
    2 プロセスで、8737 を別の Deck が使っている状態で 8738・8739 に分かれて同時に受信した
    範囲（2026-10-23・1 回）。同じ PC の別ユーザーの Deck も同じ扱いになる設計で、
    2026-10-25 に同じ PC の別アカウントで、後から起動した Deck が 8738 に分かれることと、
    そのアカウントから先に起動した側のポートへの要求が 403 になることを確かめた（n=1）
  - board.html がまだ無くてもロックは取れる（当日ボード未発行でも常駐する仕様）
  - **ロックを置けない環境では起動しない（fail-closed）**。`%TEMP%` のフォルダを作れない・
    書けない場合、同じ board への二重書き込みを避けるため常駐せずに終了し、理由を
    `watcher.log` に残す
  - 強制終了で残ったロックファイルは次の起動を妨げない。排他は OS のファイルロック
    （Windows: `msvcrt.locking` で先頭 1 バイト／POSIX: `fcntl.flock` でファイル全体）なので、
    プロセスが消えれば OS が解放する。残るファイルは次の保持者が中身を上書きする空き家にすぎない
  - 旧 `deck/deck.lock`（v1.8 以前）は残っていても無害（v1.9 は開かない。消す必要もない）。
    ただし **v1.8 の常駐が動いたまま v1.9 を起動すると、両者は別のロックを見るため
    二重起動を防げない**——版を上げるときは先に旧プロセスを止めること
- 手動起動（コンソール表示あり）: `python deck_watcher.py`
- 1 回だけ実行（テスト用）: `python deck_watcher.py --once`

### ほかのプログラムから起動するとき（Claude Code など）

Claude Code などのプログラムに Deck を起動させるとき（版を上げた後の起動し直し・止まった Deck の
起動し直し）は、**スタートアップのショートカットを `explorer.exe` で開く**。`Start-Process` で
`pythonw` を直接起動したり、`start-deck.bat` を実行させたりしない。

- **理由**: 直接起動した Deck は、起動したプログラムの子孫になり、そのプログラムが入っている
  ジョブ（Windows のプロセスのまとまり）にも入る。そのプログラムが終わると Deck も一緒に止まりうる。
  作者の PC で確かめた範囲（2026-10-28・Windows 11 Home・Claude デスクトップアプリ 4.29・n=1）では、
  Claude Code のセッションのシェルから `Start-Process` で起動した Deck は、そのシェルと同じジョブに入り、
  祖先に `claude.exe` が並んだ。同じシェルから `explorer.exe` でショートカットを開くと、Deck の親は
  DcomLaunch（`svchost.exe`）が起こした `explorer.exe` になり、シェルのジョブには入らなかった
  （その `explorer.exe` は約 60 秒で終わり、Deck は動き続けた）。同じ日、`Start-Process` で起動して
  いた作者の Deck が止まっているのが見つかった。`watcher.log` の最後の行はアプリの更新の約 5 分前で、
  エラーの行は無い。**アプリの更新が Deck を止めたのか、止めたならその機構（ジョブごと
  終わらせたのか、子孫を順に終わらせたのか）は確かめていない**
- **起動と確認は同じコマンドで行う**。起動の直後に Deck の祖先を辿り、`explorer.exe` があり、
  このコマンドを動かしているシェルが無ければ切り離せている。**間を空けると見分けられない**——
  `explorer.exe` で開いたときの親は約 60 秒で終わり、直接起動したときの親のシェルもコマンドが
  終われば消えるので、どちらも Deck より上が辿れなくなる
- 版を上げた後に起動し直すときは、先に古い Deck を止めておく（同じボードを見る Deck が動いていると、
  新しい Deck はすぐ終わる＝上の多重起動ガード）。止まった Deck の起動し直しでは、止めるものは無い。
  下の手順は起動前から動いていたものを数えず、見つけた Deck が約 3 秒後も
  動いているかを確かめるので、止め忘れは多くの場合 `TIMEOUT` か `NG` になって分かる（新しい Deck が
  3 秒より後に終わる遅い環境では `OK` と出うる。3 秒の境界は `setup.ps1` の `Invoke-DeckLaunch` と同じだが、
  あちらは `watcher.log` の終了の記録も読むので、記録が出ていれば常駐とはみなさない。下の手順は `watcher.log` を読まない）
- ショートカットが無いときは、プログラムからは起動しない（ショートカットを作らず、`setup.bat` も
  実行しない）。その旨を利用者に伝える（利用者が `setup.bat` を実行し直すと、スタートアップへの登録から
  やり直せる）。下の手順は、ショートカットが無ければ何も起動せずに `NG` を出す（ショートカットが無いと、
  `explorer.exe` を呼んでも Deck は起動せず、`TIMEOUT` と見分けにくいため）

```powershell
$lnk    = Join-Path ([Environment]::GetFolderPath('Startup')) 'today-board-deck.lnk'
$script = Join-Path $env:USERPROFILE '.claude\today-board\deck\deck_watcher.py'
$filter = "Name='pythonw.exe' OR Name='python.exe' OR Name='pyw.exe'"
$mine   = { $_.CommandLine -and $_.CommandLine.ToLower().Contains($script.ToLower()) }
if (-not (Test-Path -LiteralPath $lnk)) { 'NG: ショートカットがありません（何も起動していません）: ' + $lnk } else {
    $before = @(Get-CimInstance Win32_Process -Filter $filter | Where-Object $mine | ForEach-Object { $_.ProcessId })
    & (Join-Path $env:WINDIR 'explorer.exe') $lnk
    $deck = $null
    for ($i = 0; $i -lt 30 -and -not $deck; $i++) {   # 最大 15 秒で打ち切る
        Start-Sleep -Milliseconds 500
        $deck = Get-CimInstance Win32_Process -Filter $filter | Where-Object $mine |
            Where-Object { $before -notcontains $_.ProcessId } | Select-Object -First 1
    }
    if (-not $deck) { 'TIMEOUT: 新しい Deck が見つかりません（古い Deck が動いていないか、watcher.log を見てください）' } else {
        $chain = @(); $p = $deck
        while ($p -and $chain.Count -lt 12) {
            $chain += ('{0} {1}' -f $p.ProcessId, $p.Name)
            $q = Get-CimInstance Win32_Process -Filter ("ProcessId={0}" -f $p.ParentProcessId)
            if ($q -and $q.CreationDate -gt $p.CreationDate) { $q = $null }   # 使い回された PID は辿らない
            $p = $q
        }
        $chain -join ' <- '
        Start-Sleep -Seconds 3   # すぐ終わる 2 本目（古い Deck の止め忘れ）を OK と出さないため
        if (-not (Get-CimInstance Win32_Process -Filter ("ProcessId={0}" -f $deck.ProcessId))) { 'NG: 起動した Deck が数秒で終わりました（古い Deck が動いていないか、watcher.log を見てください）' }
        elseif (($chain -match ' explorer\.exe$') -and -not ($chain -match ('^' + $PID + ' '))) { 'OK: 起動したシェルから切り離されています' }
        else { 'NG: 起動したシェルの系統の中にあるか、親を確かめられません' }
    }
}
```

`OK` のときの最初の行は、たとえば `12140 pythonw.exe <- 39388 explorer.exe <- 1224 svchost.exe <- …` の形になる
（Python install manager で入れた場合は `pythonw.exe` が2つ続く＝下記「停止」）。この祖先の行は Deck が
見つかったときにだけ出る（ショートカットが無いときの `NG` と `TIMEOUT` では、判定の1行だけが出る）。
`NG: 起動したシェルの系統の中にあるか、親を確かめられません` のときは、その Deck を止めてから起動し直す。
起動した Deck が数秒で終わった `NG` と、`TIMEOUT` のときは、止める Deck は無い（同じボードを見る古い Deck が
動いていると、新しい Deck はすぐ終わる。見つける前に終わると、`NG` ではなく `TIMEOUT` になることがある）。
同じボードを見る古い Deck が動いていないかを `watcher.log` で確かめる。動いていれば Deck は既に動いているので、
版を上げた後でなければそのままでよい。版を上げた後なら、古い Deck を止めてから起動し直す。
古い Deck も動いていなければ、Deck は起動できていない（`watcher.log` の最後の行を見る。人が原因を確かめるときは上の「手動起動」を使ってよいが、Claude Code などのプログラムからは使わない——`python deck_watcher.py` は常駐して終わらず、起動したシェルの子孫にもなる。プログラムからは起動し直さずに、その旨を利用者に伝える）。
ショートカットが無いときの `NG` は、何も起動していないので止める Deck も無い（上の「ショートカットが無いときは」）。

## 停止

`setup.bat` を使った場合、Deck はスタートアップ（`today-board-deck.lnk`）に登録されている。

- **一時停止**: タスクマネージャーで `pythonw.exe`（コマンドラインに `deck_watcher.py` を含むもの）を
  終了する（Python install manager で入れた場合は 2 つ並ぶことがある。両方とも終了する。
  作者の PC では、どちらか 1 つを終了するともう一方も終わった）。**次回のログオンでまた起動する**
- **自動起動をやめる**: スタートアップフォルダ（`Win+R` → `shell:startup`）の
  `today-board-deck.lnk` を削除する。ボード本体（スキル）はそのまま使えるが、
  全セッションの自動集約と時刻トリガーの通知音は止まる
- **まるごと消す**: リポジトリ直下の `uninstall.bat`（常駐停止・スタートアップ解除・Deck とスキルの削除。
  ボードのデータを消すかは実行時に確認される）

PowerShell で一時停止する場合:

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'pythonw.exe'" |
  Where-Object CommandLine -match 'deck_watcher' |
  ForEach-Object { Stop-Process -Id $_.ProcessId }
```

コンソール起動時は Ctrl+C で停止。

## 仕組み

1. 5 秒間隔で `~/.claude/projects/*/*.jsonl`（トップレベルのみ・subagents 除外）の
   サイズ / mtime を監視（変化がなければ何もしない＝CPU をほぼ使わない）
2. mtime が **48 時間以内**のセッションだけを対象にする
3. **差分読み**: ファイルごとに読了バイトオフセットを `deck/state.json` に永続化し、
   追記分だけを読む。サイズが縮んだ場合のみ先頭から再パース。行単位で
   タスク関連キーワード（TaskCreate 系・`update_plan` / `wrap_up` の呼び出し）を含む行と
   利用者の入力の行だけ JSON パースする。行頭が `{"type":"api-request` の行
   （Claude Code 2.1.300 以降に記録される API リクエストの写し。過去の tool_use を含む）は
   読まずに捨てる（実測: 23.5MB の transcript で初回全量 約80ms・追記差分 約8ms〔v1.x〕／
   v2.0 は 79〜109MB の transcript 5本で初回全量 271〜433ms・v1.9 比 −8.1%〜+10.5%〔2026-10-22 測定・
   各3回の最良値〕）。
   あわせて、追記分の末尾から遡って**最後の会話イベント**（assistant / user / system の行）を
   1 つだけ読み、ターンの途中か終わったかとその時刻を持つ（v2.0）
4. タスク状態の再構築（v2.0 で多情報源化）: 情報源を次の優先順で 1 つ選ぶ。
   Claude Code 2.1.233 以降、新しいモデルでは `TaskCreate` / `TaskUpdate` / `TodoWrite` が
   既定で提供されない（環境変数 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` で戻せる）ため、
   ①だけに頼ると多くのセッションが「タスク未登録」になる
   - **① TaskCreate 系**（あれば従来どおり）: `TaskCreate`（新規）/ `TaskUpdate`
     （状態変更・deleted で削除）を時系列に畳み込む。旧形式 `TodoWrite`（全量書き直し型）は
     最後の呼び出しが最新状態。tool_use は `type` が `assistant` の行、tool_result は `user` の
     行からだけ受け付ける（API リクエストの写しで二重に数えないため）
   - **② 計画一覧**（①が無く、デスクトップアプリの `mcp__ccd_turn__update_plan` があるとき）:
     `items`（全量書き直し）・`advance`（進行中を完了にし、その後ろで最初の未着手を進行中に。
     進行中が無ければ先頭の未着手を進行中に）・`done` / `start`（1 始まりの番号。`start` は
     ほかの進行中を未着手へ戻す）を畳み込む。`mcp__ccd_turn__wrap_up` が呼ばれたら、一覧は
     **表示でだけ**全完了として数える（道具の説明が逐語「it also checks off the task list」と
     書くため）。畳み込んだ一覧そのものは書き換えず、次の `update_plan` で表示も元に戻す——
     アプリ側の一覧は wrap_up で書き換わらず、wrap_up の後の `advance` にアプリは wrap_up 前の
     一覧を基準にした「step K of M」を返すため（実測 2026-10-22・フォーク関係の 2 セッションで計 4 回）。
     task-note は「現在の項目 ・ 完了N / 全M ・ ターンの状態 ・ 最終更新 ・ 出所: 計画一覧」
   - **③ 活動**（①②が無いとき）: 最後の会話イベントから判定したターンの状態だけを出す。
     task-note は「ターンの状態 ・ 最終更新 ・ 出所: 活動」。会話イベントも無ければ従来どおり
     「タスク未登録」
   - **ターンの状態（②③共通）**: 最後の会話イベントが assistant の `end_turn` /
     `stop_sequence`・system の `stop_hook_summary`・利用者の中断（`[Request interrupted by user`）
     なら「ターン終了」、それ以外（利用者の入力・tool_result・tool_use で止まった assistant）なら
     「ターンの途中」。利用者の新しい入力（中断を除く）でそのターンの `wrap_up` を忘れる。
     **利用者の入力とみなすのは、`turnOrigin` が無いか `human` で、`origin.kind` が無いか
     `human` で、本文（ブロック列なら text ブロックごと）の先頭に続く `<system-reminder>` /
     `<task-notification>` / `<cross-session-message>` を閉じタグまで取り除いても文が残る
     user 行だけ**——アプリや別のセッションが差し込む行（起動したセッションの完了通知・
     サブエージェントの完了通知・別セッションからの連絡など。`turnOrigin` は `sdk` /
     `task_notification` / `peer` 等。2.1.304／2.1.308 のサブエージェント完了通知は
     `turnOrigin` を持たず `origin.kind` が `task-notification`）は問いを消さない
     （消すと、未回答の問いが「済」に見える）。書き出しだけで判定しないのは、アプリが利用者の
     入力の先頭に `<system-reminder>…</system-reminder>` を付けることがあるため
     （実測 2026-10-22・直近 60 日で 9 件）。閉じタグの無い差し込みは取り除けないので、
     利用者の入力とみなさない。差し込み行もモデルを動かすので、
     ターンの状態としては「途中」に数える
   - **計画リンク（v1.5）**: TaskCreate の入力に `metadata: {"plan": "<計画タスク名>"}` が
     あればタスクごとに保持し、カードの task-note 末尾に「／計画: <plan名>」を表示する。
     plan の選択は「表示対象タスクの plan → 無ければセッション内で最頻の plan（同数なら
     先に作成された方）→ それも無ければ非表示」。metadata の無いタスクは従来どおり
     （後方互換・表示なし）
   - **計画リンクは①でのみ出る**。`update_plan` には計画タスク名に当たる欄が無いので、
     ②③のカードには「／計画: …」を付けない（推測で補わない）
   - **チップ判定（①）**: ⓪利用者への問いが未回答（下記「回答待ち」）→「保留」。全タスク
     完了でも「済」にせず、task-note の「完了N / 全M」の後に問いを添える（v2.0）
     ①全タスク完了 →「済」 ②in_progress が 1 件でもある →「進行中」
     ③in_progress が無く、件名が「【承認待ち】」で始まる pending タスクがある →「保留」
     （ユーザー承認待ちセッションの可視化・運用ルール: 承認待ちタスクは件名を
     【承認待ち】で始める） ④それ以外 →「未」（タスク未登録・読取不能も「未」）
   - **回答待ち（①②③共通・v2.0）**: (a) 最後の会話イベントが結果待ちの `AskUserQuestion`
     （時間が経っても同じ。問い文を添える） (b) このターンの `wrap_up` に `ask` か `blocked: true`
     があり、いまモデルが動いていない（`blocked` なら「返答待ち（作業停止中）」、それ以外は
     「確認待ち」。`ask` の文を添える）
   - **チップ判定（②③）**（上から最初に当てはまるもの）: ⓪回答待ち →「保留」
     ①ターンの途中で、最後の動きから 15 分以内 →「進行中」（作業中）
     ②ターンの途中のまま 15 分を超えて動きが無い →「未」。結果待ちの道具が `Agent` /
     `Task` / `SendMessage`（サブエージェント待ち）なら「15分以上動きなし」、それ以外は
     「応答なし」 ③このターンの `wrap_up` がある（問いなし）→「済」（完了報告あり。
     `recap` を添える）
     ④ターン終了 →「入力待ち」。チップは計画一覧が全完了なら「済」、それ以外は「未」。
     「作業中」→「応答なし」／「15分以上動きなし」は transcript が動かなくても時間経過で起きるので、常駐ループは
     その時刻に再生成する（①も含む。差し込み行で保留が外れたカードを戻すため）
5. 「最終更新」の時刻と並び順は**最後の会話イベントの時刻**（v2.0）。transcript の mtime は
   会話が無くてもタイトル行等の追記で進むため（本人環境で、8 月に止まったセッションの mtime が
   当日になっていた）。会話イベントの時刻が取れないときだけ mtime を使う。対象の絞り込み
   （48 時間以内）は従来どおり mtime で行う。
   セッションのラベル: `custom-title`（ユーザー命名）→ `summary` → `ai-title`（自動命名）の
   優先順。どれも無ければ「プロジェクト名 + セッションID先頭8桁」
6. プロジェクト名は transcript 各行の `cwd` から取得。取れなければエンコード済み
   ディレクトリ名で代用。worktree はランダム名がノイズになるため
   「プロジェクト（作業コピーN）」表示（例: `myapp（作業コピー1） — …`）。
   N はプロジェクトごとに初めて観測した順の連番で、state.json に永続化して
   再生成をまたいで安定させる（worktree が 1 つでも「作業コピー1」）
7. タスクが 1 件もないセッションも一覧に出す（②③の表示、どちらも無ければ「タスク未登録」。
   目的＝開いている全セッションが 1 枚で見えること）
8. **同名セッションの畳み込み（v1.2）**: (プロジェクト, タイトル) が同一のセッション群
   （resume / fork の重複）は最終更新（上記5の時刻・v1.x は mtime）が最新の 1 枚だけ表示し、task-note 末尾に
   「（他N件を畳み込み）」を付ける。タスク集計は代表セッションのもののみ（合算しない）
9. **`data-sid` 属性（v1.2）**: 各カードの `<div class="item flat">` に
   `data-sid="<セッションID>"` を付与（畳み込みカードは代表セッションの ID。
   「タスク未登録」「読取不能」カードにも付与）。board.html 側のカード非表示機能が参照する
10. board.html のマーカー間を置換し、あわせて手書きセクションの完了表示を状態チップに
    合わせて整合させ（v1.8・`class` トークンの足し引きのみ）、一時ファイル → `os.replace` で
    アトミックに書き込む（どちらにも差が無ければ書き込みしない）

board.html 側の挙動:

- board.html が存在しない（当日未発行）→ 警告ログのみでスキップし、監視は継続。発行されたら自動で反映
- マーカーが2つとも無く、コメントの外に Deck が書いた部分が残っている → その部分が空行だけを挟んでひと続きなら、
  前後にマーカーを足して囲んで書く（v2.5・ログに1行）。Deck が書いた部分＝`id="deck-key"` と `id="deck-lastgood"` の span・
  「監視ねこ」と「全セッション（自動収集 …）」の見出し・`data-sid` の付いたカード・「アクティブなセッションなし」のカード・
  「監視ねこ」の見出しの直後の1行のうち Deck が書く形のもの（`task-title` が無く、チップの欄
  `<div class="chips" style="margin-top:0">` が先頭にあり、`task-note` が「ログ退避 ・ 」で始まる）だけ（`skill/SKILL.md`
  「ボードの点検」の②と同じ対象。コードは `deck_written_part`）。間にそれ以外の行（ユーザーの行・コメントの行・
  閉じタグが対応しない項目）が挟まる → 何もしない（ユーザーの行を囲まない。警告ログに理由と行の番号）。
  Deck の部分の外側（前・後ろ）にある行は見ない——見分けられない行があっても、Deck の部分だけを囲み、その行は目印の外に残す。
  見分けられない行の扱いは SKILL.md ②と違う（Claude は見分けられない行があればユーザーに聞く）
- マーカーが2つとも無く、Deck が書いた部分も無く、コメントの外の `<footer>` がちょうど1つ → その直前にマーカーを足して書く
  （v2.2・ログに1行）。`<footer>` が無い／複数 → 何もしない。警告ログのみ
- マーカーが片方だけある・順序が逆（最初の START の後ろに END が無い）→ 何もしない。警告ログのみ。目印が多くても、最初の START の後ろに END があれば、その間に書く（余分な目印は消さない）
- board.html が外部（today-board スキル等）から書き換えられた場合も検知して再挿入する

## 日付の切り替え（v2.2）

2026-10-25〜27 に、複数のセッションが today-board スキルを通さずに board.html へ直接書き足し続け、
新しい日のボードが2日間発行されなかった。日付の古い板では board.js の発行済みボード判定が偽になり、
Deck への書き込み4経路（通知音の設定・時刻上書きの中継・通知の確認・D&D の反映）が止まる。
そこで日付の切り替えを Claude の手順から外し、Deck が持つ。

- **「今日」** は PC のローカル時刻の暦日（0:00 で切り替え）。board.js の発行済みボード判定と同じ暦日で、
  日付の読み方も同じ（4桁の年あり→年月日／年なし→月日。年なしは今年とみなし、半年より先なら前年）
- **確かめる契機**: 常駐の毎周回のうち、board.html が変わったとき・日付が変わったとき・前回が待ち／中止／
  失敗／例外だったときだけ（毎周回は読まない。例外のあとは、その日の試行が上限に達していれば試さず、
  そうでなければ60秒以上空ける）。起動直後の1周目にも走る（朝のログオンで Deck が起動したとき）。スリープからの復帰では Deck は起動し直さないので、復帰後の最初の周回で「日付が変わった」として確かめる（コードの読解による）
- **切り替える条件**（すべて満たすとき）: ①ヘッダの日付が読めて今日より前 ②board.html と同じフォルダの
  `config.json` の mode が `artifact` でない ③同じフォルダの `state.json` に `url` が無い ④`state.json` の
  `file_path` が無いか、このボードと同じファイル ⑤DECK マーカーがちょうど1組 ⑥ボードの構造が崩れていない
  （項目の入れ子・閉じタグの欠落が無く、今日の予定の時刻付きの未完了の項目は、時刻の要素がちょうど1つ） ⑦その日の試行が10回未満（失敗・中止のあとは60秒以上空ける）
- **引き継ぎ**（元のボードを変形して作る。テンプレートは使わない）:
  今日の予定＝済は捨て、時刻付きの未完了は今日中の先頭へ移す（`.time` を外して `flat` を付け、元の時刻を
  `data-orig-time` に残す。そのままだと昨日の 9:00 が今日の 9:00 に鳴るため）／今日中・プロジェクト名の
  セクション＝済は捨て、残りを引き継ぐ（空になったプロジェクト名の見出しは除く）／ルーチンタスク＝全部残し、
  済を未に戻す／明日以降＝そのまま。引き継いだ行には `data-carried-from="<元の日付>"`、`<div class="board">` には
  `data-tb-rolled="<元の日付>"` を付ける。DECK マーカーの間はバイト列そのまま。ヘッダの日付・`<title>`・
  `#upd-time`（切り替えた時刻）・進捗は今日の値にする
- **退避**: 元のボードを `history/board-<元の日付>.html` へバイト列のまま書き、読み返して一致を確かめてから
  差し替える。同名があれば `-2`、`-3` …を付ける。**自動では消さない**
- **重なった書き込み**: `_BOARD_LOCK` の中で読み直し、作り始めたときから board.html が変わっていたら中止して、
  次の機会（60秒後以降）にやり直す。Claude の書き込み（`board_edit.py`。それより前の SKILL.md では一時ファイル→`Move-Item`）は Deck のロックの外なので、
  最後の確認から差し替えまでの短い間に入った書き込みは検出できない（`[推定]` 頻度は低い・未計測）。
  日付が変わる前に読んだ書き手が古い日付のボードを書き戻した場合は、前の試行から60秒以上たった後の周回で
  もう一度切り替わり、書き戻された行も引き継がれる（その日の試行は上限10回）
- **state.json**: 切り替えたら `date` を今日にする（ほかのキー・キーの順・BOM・改行の形は保つ。JSON の字下げは2に
  書き直す）。今日のボードなのに `date` が今日と違うときもそろえる。いずれも local モードで `url` が無く、
  `file_path` が無いか、このボードと同じファイルのときだけ（上の条件④と同じ）
- **静的ファイル**: 切り替えたとき、スキルの `assets/`（既定 `~/.claude/skills/today-board/assets/`）の
  `board.css` / `board.js` / `cat.png` のうち中身が違うものを board.html の隣へ写す
  （スキルの create モード6 で `board_edit.py` の create が写すのと同じ。Claude の create を通らない日にも新しい版が届くようにするため）。
  v2.3 からは、切り替えとは別に、常駐の起動時と5分ごと（`ASSET_SYNC_SEC`）にも同じことをする（下記）
- **失敗したとき**: 差し替えは一時ファイル→`os.replace` なので、どこで止まっても元のボードは無傷。
  理由は `watcher.log` に1行出る
- **画面の側（board.js）**: 「引き継いだボード」の知らせと、行ごとのチップ（例「↪ 10/26 9:00 の予定から」。時刻が無ければ「↪ 10/26から」）を出す。
  知らせの元の `data-tb-rolled` は、切り替えの後に Deck 以外の書き手が手書き部分を変えた時点で Deck が外す
  （v2.3・下記）。行ごとのチップの元の `data-carried-from` / `data-orig-time` は外さない。
  今日でない板には「書き込み停止中」の知らせを出し、Deck が動いている過去日の板では、Deck が今日の板を作るのを
  待つため90秒は出さずに60秒の時点で1回だけ読み直す。どの板でも 0:00 から20秒後に1回読み直す

### Deck が計算し直すヘッダの値（v2.2）

- 進捗（N / M とバー幅）と `<title>` の日付は、Deck がマーカー間を書き直すたびに計算し直す。D&D の反映では
  進捗だけを計算し直し、`<title>` は次にマーカー間を書き直すときにそろう（board.html が変わると数秒以内に走る）
- `#upd-time`（タスク更新）は、手書き部分（ヘッダの日付と、DECK マーカーの外のセクション見出しと項目。Deck が
  直す値は除く）の
  指紋が **Deck 以外の書き手**で変わったとき、そのファイルの更新時刻にする。Deck 自身の書き込み（D&D の反映・
  日付の切り替え）では動かさない。起動直後は今の値を正として覚えるだけ（止まっていた間の変化は反映しない）
- `data-tb-rolled`（引き継いだボードの印・v2.3）は、手書き部分の指紋が Deck 以外の書き手で変わったときに外す。
  朝の計画が create を通らず update で行われても、知らせが出続けないようにするため。判定は、切り替えたときの指紋を
  `<div class="board">` の `data-tb-rolled-fp`（16桁）に持たせて今の指紋と比べる——メモリの指紋と違い、Deck が
  止まっている間に変えた板も、起動直後の1周目で外れる（外すときは `data-tb-rolled-fp` も一緒に外す）。
  誰も触らなければ外さない。Deck 自身の D&D の反映は、動かす前の板の指紋が `data-tb-rolled-fp` と合っていれば、
  書き込みと同時に `data-tb-rolled-fp` を新しい値にするので外れない（合っていなければ書き換えず、次の再生成で外れる）。
  Deck が直す値（`#upd-time`・進捗・`<title>`・`done-item` / `strike`）だけの書き換えでは外さない。
  `data-tb-rolled-fp` を持たない板（v2.2 で切り替えた板）だけは、`#upd-time` と同じくメモリの指紋の変化で判定する。
  印（`data-tb-rolled`）が無いのに `data-tb-rolled-fp` だけが残っている板（書き写し等）では、その指紋を外して片付ける。行の `data-carried-from` / `data-orig-time` は外さない
  （その行が済になって次の切り替えで除かれるか、create で書き直されるまで残る。重ねて切り替えても最初の値を保つ）

### 形が崩れたときの退避（v2.4）

- Deck はマーカー間を書き直すために board.html を読むたび（board.html か transcript が変わったときなど）に形を
  確かめる（`board_structure_ok`＝`_scan_board` がすべての項目を拾えるか。項目の入れ子・閉じタグの欠落があると偽）。
  日付の切り替え・通知音の判定・D&D の反映のために読むときは確かめない。形が正しい版のバイト列を、メモリに1つだけ持つ
  （`LASTGOOD_MAX_BYTES`＝2MB まで。超える版は持たない。マーカー間を書き直して書いた版も形を確かめ、正しい形なら、それに持ち直す）
- 正しい形から崩れた形に変わったのを見つけたら、持っていた版を `history/board-<その版の日付>-lastgood-<HHMMSS>.html`
  （`<HHMMSS>` は退避した時刻）へ書き（同名があれば `-2` 等）、`watcher.log` に1行残す。崩れが続く間は退避し直さない。形が正しく戻った後に
  また崩れたら、もう一度退避する
- 退避した間は、DECK 領域に `<span id="deck-lastgood" hidden data-file="history/…">` を書き、board.js が
  「ボードの点検」の知らせに、崩れる前の版を残したことを添える（board.js が読むのは目印の間にあるものだけ・2026-10-29）。形が正しく戻ると目印は消える。崩れたまま
  Deck を起動し直したときも、目印は消える（起動した Deck は崩れる前の版を持っていないため。退避したファイルは
  `history/` に残る）
- **Deck は板を直さない**（直すのは利用者か Claude）。起動した時点で既に崩れていた板は、崩れる前の版を
  持っていないので退避せず、ログに1行だけ残す

### 静的ファイルの同期（v2.3）

- 常駐の起動直後の1周目と、そこから5分ごと（`ASSET_SYNC_SEC`＝300 秒。ページの自動再読み込みと同じ間隔）に、
  スキルの `assets/` の `board.css` / `board.js` / `cat.png` と board.html の隣の3点を中身で比べ、違うものだけ写す
- **本番スキルを正とする**（更新時刻では比べない）。配る順は「リポジトリ → 本番スキル → 実行系」
  （today-board スキルの create モード6〔`board_edit.py` の create が写す〕も本番スキル → 実行系の向き。`setup.ps1` はリポジトリの `skill/` から本番スキルと
  実行系の両方へ写す）で、実行系は生成物＝利用者が編集する場所ではない。
  したがって実行系だけを先に新しくしても、5分以内に本番スキルの版へ戻る
- 写し元のフォルダが無い・写し元と board.html のフォルダが同じ・board.html のフォルダが無いときは何もしない。
  写したときだけ `watcher.log` に1行出る
- 写し元が書きかけのときは写さない: 更新時刻が5秒以内（`ASSET_SETTLE_SEC`）のもの、読む前と後で大きさか更新時刻が
  変わったものは見送り、次の機会に写す
- `--board` で既定以外のボードを指し、`--skill-assets` を渡していないときは、この同期も日付の切り替えでの写しも
  行わない（起動時に `watcher.log` へ1行出る）。`--skill-assets` を明示すれば、そこから写す

### 書き込みの記録と読み直し（v2.6）

today-board スキルのガード（board.html を書き換える手段を同梱のスクリプト `scripts/board_edit.py` に限り、それ以外の
書き込みを止める・戻すしくみ）は、正規の書き手が残す記録を見て、Deck の書き込みを正規と見分ける。そのため Deck は次のようにする
（ガードが入っていない環境では、記録は読まれない）。

- **書き込みの記録**: 手書き部分の指紋（ヘッダの日付と、DECK マーカーの外のセクション見出しと項目。上記「Deck が計算し直す
  ヘッダの値」と同じ指紋）を変える書き込み——D&D の反映・日付の切り替え・マーカーを足して指紋が変わるとき——の**前に**、
  board.html と同じフォルダの `.guard/auth/` へ記録を1件書く（`<時刻 ns 20桁>-<pid>.html` に書く版の本文、
  `<時刻 ns 20桁>-<pid>.json` に `{"v": 1, "fp": 書く版の指紋, "base_fp": 読んだ版の指紋, "writer": "deck", "body": 同名の .html}`）。
  指紋を変えない書き込み（ふだんのマーカー間の書き直し・完了表示の整合・ヘッダの値）では書かない。
  置き換えられなかったときは、自分の記録を消す。48時間より古い記録は、記録を書くときに消す（`board_edit.py` の記録も同じ規則で消す）
- **`.guard/format.json`**: 無ければ `{"v": 1}` で作る（あれば上書きしない）。知らない版のとき・読めない（壊れている）ときは、
  記録を書かずに板を書き、`watcher.log` に1行残す（同じ版のあいだは繰り返さない。直しも上書きもしない）。
  記録そのものを書けない（`.guard/auth/` を作れない等）ときは、板を書かない（理由は `watcher.log`）
- **`.guard/` の守られ方**: ガードが止めるのは、Claude が Write・Edit などで `.guard/` へ直接書くことだけである。
  Bash・PowerShell から書いたものは止めず、後から戻すこともしない（後から戻すのは board.html だけ）
- **置き換える直前の読み直し**: 書く直前に board.html を読み直し、読んだときのバイト列と違えば（ほかの書き手が書いた）書かない。
  マーカー間の書き直しはその周回を見送り、次の周回で読み直す。D&D の反映は読み直した板にもう一度当てる（最初の1回を含めて3回まで）。
  日付の切り替えは中止し、次の機会（60秒後以降）にやり直す
- **置き換えのやり直し**: `os.replace` が `PermissionError`（ほかのプログラムが board.html を読み取りで開いている等）なら、
  0.2 秒あけて5回までやり直す。やり直す前にも読み直して比べ、違えば上の読み直しと同じに扱う（待つ間にほかの書き手が
  置き換えた版を消さないため）
- **D&D の反映の時間の上限**: 要求を受けてから1秒（`MOVE_DEADLINE_SEC`）以内に書けなければ、書かずにやめる
  （ほかの書き込みが終わるのを待つ時間も含む）。board.js が答えを待つのをやめる1.5秒より短くして、board.js が
  「保存できませんでした」と知らせた移動を、後から Deck が書くことの無いようにするため
- 記録の形式・名前の決め方・消し方の関数は `board_edit.py` と同じもの（写し）を使う

壊れやすさへの防御（transcript 形式は Claude Code の内部仕様でバージョンにより変わりうる）:

- 個々の行のパース失敗 → その行だけ捨てて継続
- ファイル単位の読取失敗 → ログに残し、ボードに「(読取不能: <ファイル名>)」カードを出す
  （沈黙して消えない）

## ボードD&D移動の受け口（v1.6）

board.html のブラウザ表示では、タスクを「今日の予定 / 今日中 / 明日以降」の
3セクション間でD&D移動できる（board.js 実装済み）。Deck 常駐中はこの移動を
HTML 正本へ自動反映する。

- 常駐監視モードでのみ `http.server.ThreadingHTTPServer` を **127.0.0.1 の 8737〜8746 の
  うち空いている最初の 1 つ**にバインドして受信する（`--once` では起動しない）。受信専用で
  外部への送信はしない。どのポートを取ったかは `watcher.log` の「受信サーバ起動」の行に出る
- 10 個すべてバインドできない場合は `watcher.log` に記録し、サーバ無しで通常動作を継続
  （下記「受信ポートと照合（v2.1）」の「ポートが取れないとき」）
- エンドポイント（`/ping` 以外は、すべてクエリ `?board=<ボードの URL>&k=<トークン>` が要る。
  下記「受信ポートと照合（v2.1）」）:
  - `GET /ping` → 200・body `deck-board-mover`（稼働確認用・`?board=`・`k` 不要）
  - `POST /board/move` → body は JSON（Content-Type 不問）:
    `{"k": "<key>", "sec": "今日の予定|今日中|明日以降", "before": "<key> または null", "head": true}`
    - `k` は board.js の key() と同一定義:
      `(time のテキスト + '|' + task-title のテキスト).trim()`（タグ除去・エンティティ復号済み）
    - `head`=true でセクション先頭、`before` 指定でその item の直前、どちらも無ければ末尾
  - 成功 → 200・`{"ok": true}`／Host・Origin が外れる、トークンが無い・違う、`?board=` が
    無い・読めない・このボードではない → 403／不正 JSON・不正 sec → 400／key 不一致 → 404／
    内部エラー → 500／board.html を書けなかった（置き換えのやり直しを使い切った・置き換えの前の読み直しが
    `PermissionError` で読めなかった・書き込みの記録を書けなかった）→ 500、
    書く直前にほかの書き手が書き、3回試して3回とも書けなかった → 409、1秒以内に書けなかった → 503（いずれも
    `{"ok": false, "error": "移動を board.html に書き込めませんでした"}`・v2.6。board.js はこの文を表示しない）
- 全レスポンスに CORS ヘッダ（`Access-Control-Allow-Origin: null` 等・
  `OPTIONS` は 204 + Private Network Access ヘッダ）。file:// で開いたボードからの
  fetch を通すため。許すオリジンは `null`（file:// のページ）だけ（v2.1。v2.0 までは `*`）
- 移動の適用は「手書き3セクション間の item ブロック再配置＋進捗行
  （`N / M 完了`・バー幅）の再計算」のみ。**DECK マーカー間には一切触れない**
  （走査対象からも除外）。inject と同一プロセス内の lock を共有し同時書き込みを防ぐ
- board.js 側: ドロップ時に POST を試行（タイムアウト1.5s）。200 なら localStorage に
  保存しない（ファイルが正）。Deck 停止中・失敗時（403 を含む）は従来どおり localStorage 保存に
  フォールバック＝**Deck が未起動でも何も壊れない**。Deck が 200 以外を返したとき（403・409・500・503 等）と、1.5秒以内に
  答えなかったときは、localStorage に保存したうえで、画面の右下に「移動を保存できませんでした。このブラウザの表示にだけ残り、
  ボードのファイルには入っていません。もう一度動かしてください。何度やっても出るときは、動かした項目と行き先を Claude に伝えてください」と出す（クリックで消える。2026-10-30）。何度やっても失敗するのは、`.guard/auth/` を作れない・書けないとき（500）、board.html が無い・UTF-8 として読めないとき（500）、項目が board.html に見つからないとき（404）、このボードを見ていない Deck が答えたとき（403）などで、理由は `watcher.log` の「移動受信: … → 500」等の行に出る。
  Deck に接続できない
  （止まっている）ときは出さない（「監視ねこ」の行が Deck の停止を示す）。v2.5 以前の Deck は時間の上限を持たないので、
  1.5秒を過ぎてから書くことがあり、そのときは知らせが出ても board.html には入っている
- 受信した移動（k・sec・結果コード）は `watcher.log` に1行記録される

## 時刻トリガーの通知音と未確認通知（v1.7）

通知音の発音をブラウザ（board.js の WebAudio）から Deck 側へ移した。

**理由**: ブラウザの自動再生制限により、ページ上でユーザー操作が一度も無いと
`AudioContext` が running にならず無音のまま終わる。board.html は 5 分ごとに全リロード
されるため、クリックで得た解除も最大 5 分で失効する。この道具の想定用途は
「サブモニタに置いて触らない」なので、ページ内再生では構造的に鳴らない。

- **通知音の既定は OFF**。ボードの⚙パネルで ON にすると board.js が設定を Deck へ送る
- **通知音の ON/OFF と音種は Deck だけが持つ**（`sound.json`・2026-11-02 以後の board.js）。board.js は読み込みのとき
  `GET /sound/config` で読んで⚙に表示するだけで、送るのは⚙を操作したときだけ。操作の直前に読み直し、変えない項目は読んだ値で
  埋めて `POST /sound/config` で送る（読めなければ送らない）。ボードを開いただけでは、どのブラウザでも設定は変わらない（試験はサンドボックスの Deck と、ヘッドレスの Chrome・Edge で行った。実際に使っているボードでは、2026-11-02 にふだんのタブと別のブラウザ〔Chrome〕で開いて、ON のまま変わらず同じ設定が出ることをユーザーが目視した〔各 1 回。ふだんのタブのブラウザ名は記録に無い。時刻に鳴るかは未確認〕）。
  試聴は読んだ値をそのまま送るので設定を変えない。音種のボタンは選んで試聴する（いまの音種を押しただけなら設定は変わらない）。
  Deck から読めないとき（止まっている・この環境に無い・別の場所へ写したボード・トークンが古い・接続情報が無い＝監視ねこの「停止」「写し」「古い」「不明」など）は⚙の通知音を操作できず、
  値の代わりに「—」と知らせを出す（Deck を起動し直したときは接続情報が替わるのでページが読み直され、操作できるようになる。サンドボックスの Deck〔transcript の無い状態〕とヘッドレスのブラウザでは、起動から約7秒だった。前の読み直しから60秒たっていないタブでは、60秒たつまで待つので最長で1分ほどかかる〔続けて起動し直したときは約57秒〕。Deck が新しい接続情報を書くのが最初の読み直しに間に合わないときも、同じ待ちになる〔コードを読んだ範囲で、動かしては確かめていない〕。同じ Deck の応答が戻っただけなら、3秒ごとの確認で設定を読み直す。写しのボードでは、Deck が動いていても操作できない）。今日でないボードでは、読めれば値を表示するが操作はできない
- Deck は board.html の時刻付き・未完了タスクを 5 秒ごとに判定し（board.html を読み直すのは変化したときだけ）、予定時刻に達したものを
  `winsound` で鳴らす（`SND_MEMORY` で合成 WAV を再生。失敗時は `Beep` へ退避）。
  **`winsound` の無い環境（非 Windows）では鳴らさずに継続する**
- 予定時刻を 5 分以上過ぎた分はまとめて鳴らさない（board.js と同値）
- **ポップアップは Deck が無くても出る**（board.js のローカル経路）。Deck 稼働中は
  「未確認通知」を Deck 側が保持し、board.js が 3 秒ごとに取りに来て描画するため、
  **ページをリロードしても未確認分が復元される**
- 完了判定は状態チップを唯一の真実とする。`done-item` / `strike` は表示用の派生情報で、
  board.js が表示時に DOM へ付け外しし、**Deck 稼働中は v1.8 の整合が HTML 正本側も
  同じ規則で揃える**（Deck 停止中は正本に不整合な記述が残りうる。表示は board.js が吸収する）
- ✎ による時刻の手動変更は board.js の localStorage にしかないため、`POST /board/times`
  で中継してもらい、上書きがあればその時刻で発火判定する。起動時に送るのは、そのブラウザに今日の上書きの記録があるときだけ
  （2026-11-02 以後の board.js。全部外した後も空の記録が残るので、空の地図が届いて元の時刻へ戻る）

追加エンドポイント（いずれも 127.0.0.1 の受信ポート・受信専用・`?board=` と `k` が要る。
無い・読めない・違う要求は読み取りも書き込みも 403）:

- `GET /sound/config` → `{"ok":true,"enabled":<bool>,"type":"std|chime|pip|bell"}`
- `POST /sound/config` → `{"enabled":<bool>,"type":"<音種>","test":<bool>}`（`test`=true で試聴）
- `GET /board/times` → 現在保持している時刻上書き／`POST /board/times` → `{"ovr":{...}}` で全置換
- `GET /notifications` → 未確認通知の一覧 `{"ok":true,"deck":"today-board","items":[{"key","time","title"},...]}`
  （`deck` は v2.1 で足した目印。board.js は 200 とこの目印がそろったときだけ「稼働」と描く）
- `POST /notifications/ack` → `{"keys":[...]}` で確認済みにする（ユーザーがトーストを閉じたとき）

## 受信ポートと照合（v2.1）

127.0.0.1 のポートは PC 全体で共有される。v2.0 までは 8737 固定で、要求がどのボードから
来たかを確かめていなかったため、同じ PC で 2 人の Windows ユーザーが使うと
①後から起動した Deck はポートを取れず、D&D 反映・通知音の設定が効かない
②もう 1 人のボードでの操作が先に起動した人の Deck に届き、その人の `sound.json` や
board.html を書き換えうる——の 2 つが起きうる作りだった（コードの読解による。2 人の
Windows ユーザーで実際に起きることは確かめていない）。v2.1 はこれを次のように扱う。

- **ポート**: 8737 から順に 8746 まで試し、最初にバインドできたもので受信する。
  使用中のポートは飛ばす（Windows ではバインドが失敗するよう `SO_REUSEADDR` を使わない）。
  確かめたのは、別の Deck が使っているポートを飛ばす場合で、同じユーザーの Deck（2026-10-23）と
  同じ PC の別アカウントの Deck（2026-10-25。後から起動した側が 8738 で受信した・n=1）の 2 つ。
  他のプログラムが使っている場合は未検証。8737 以外になった場合は
  `watcher.log` に「受信ポート 8737 は使用中のため 8738 で受信します」の形で出る
- **トークン**: Deck は常駐の起動ごとに乱数のトークン（`secrets.token_urlsafe(32)`＝43 文字）を
  作り、受信ポートと一緒に board.html の DECK:AUTO 領域の先頭へ
  `<span id="deck-key" hidden data-port="<ポート>" data-k="<トークン>"></span>` として書く
  （画面には出ない）。board.js はこれを読み（DECK:AUTO の目印の間にあるものだけ。目印の外に残った古い接続情報は
  読まない・2026-10-29）、**そのポートへだけ** `&k=<トークン>` を添えて送る
  （ポートを順に探して回ることはしない＝トークンを他のプロセスへ送らない）。Deck は
  `hmac.compare_digest`（定数時間）で比べ、無い・違う要求を 403 で断る。
  - **なぜ board.html に置くか**: 外部のサイトのページ（sandbox iframe を含む）はローカルの
    board.html を読めず（ブラウザの権限による。実ブラウザで確かめたのは、トークンを知らない
    sandbox iframe の要求が断られることまでで、board.html そのものを読めないこと・手元の別の
    HTML〔file://〕から読めないことは試していない）、別の Windows ユーザーは他人のプロファイルの
    board.html を読めない（OS の既定の権限による・未検証）。そのため、ブラウザで開いたページの
    うちトークンを知りうるのは、このボードを開いたページだけになる（ページ以外で知りうるものは
    下の「限界」）
  - **なぜ起動ごとか**: ファイルに永続させないので、`deck/` に置くものが増えない。Deck を
    止めて起動し直せばトークンが替わる。`--once` は接続情報を書かない（常駐が書いた値を
    別の値で上書きしないため。消えた分は常駐が board.html の変化を検知して書き戻す）
  - **発行直後・Deck 再起動の直後**: ボードを発行した直後は DECK:AUTO 領域が空で、Deck が
    数秒以内に接続情報を書き込む。board.js は接続情報が無ければ要求を出さず（発行直後は「監視ねこ」の見出しもまだ無いので、生死の行は出ない。見出しがあって接続情報だけが無い板では「不明」）、
    8 秒後に 1 回だけページを読み直す（同じタブでは 1 日 1 回まで。Deck を入れていない環境で
    読み直しを繰り返さないため）。Deck を再起動するとトークンが替わり、開いたままのページの
    要求は 403 `"token mismatch"` になる。board.js はそれを受けて 6 秒後にページを読み直し、
    新しいトークンで続ける（同じタブでは 60 秒に 1 回まで）。同じトークンのまま 2 回読み直しても
    変わらない（Deck がそのファイルを書いていない＝別の場所へ写したボード等）ときは、それ以上は
    読み直さず、「監視ねこ」に「古い」とその旨を出す（1 回目で止めないのは、遅い PC で Deck の最初の
    書き込みが 6 秒の待ちに間に合わなかっただけの正しいボードを行き詰まり扱いにしないため。
    5 分ごとの再読み込みは続く。2026-10-26 の修正以後の board.js。それより前の版は約 60 秒ごとに
    読み直し続けうる作りだった＝コードの読解による）。どちらも、外れても 5 分ごとの
    自動再読み込みで追従する。この2つの読み直しは発行済みの今日のボードだけ（今日でない板の読み直しは
    上記「日付の切り替え（v2.2）」の画面の側を参照）。実ブラウザで確かめたのは
    再起動後の読み直し（Chrome は下の②。2026-11-02 にヘッドレスの Edge 156〔2 回〕と Chrome〔1 回〕で、サンドボックスの Deck〔transcript の無い状態〕を起動し直して確かめた。1 回目は起動から約 7 秒、続けてもう一度起動し直すと約 57 秒で操作できるようになった。実際の transcript がある環境では測っていない）で、発行直後の読み直しは試していない
  - **ほかの書き換えとの関係**: today-board スキルの create（`board_edit.py` の create）は、いまの板に
    マーカーが1組あれば DECK:AUTO 領域をそのまま引き継ぎ（無ければ領域は空になる）、update（`board_edit.py` の
    操作）は領域に触れない（古いトークンが残っていても、Deck が数秒以内に今の値で書き直す）。D&D の反映と
    完了表示の整合は DECK マーカー間に触れないので、接続情報を消さない
  - `[実測]` 2026-10-23・ヘッドレスの Chrome 155.0.8059.86 と Edge 155.0.4283.62・各 1 回:
    ①file:// のボードから、自分の Deck に設定の POST が届いた（Chrome・Edge）
    ②ボードを開いたまま Deck を再起動すると、403 `"token mismatch"` の後にページが読み直され、
    新しい Deck に設定の POST が届いた（Chrome のみ）
    ③公開サイトを模した `http://localhost` のページに `<iframe sandbox="allow-scripts">` を置き、
    ボードのパスを当てた要求を送ると、`GET /notifications`（トークン無し・当て推量）と
    `POST /sound/config`（トークン無し）はすべて 403（`"token required"` / `"token mismatch"`）で、
    `sound.json` は変わらなかった（Chrome・Edge）。iframe が読めたのは 403 の理由の文字列だけで、
    通知・設定の中身は読めなかった
- **申告**: board.js は Deck への全要求に `?board=<location.href から # と ? 以降を除いたもの>`
  を付ける（例 `?board=file%3A%2F%2F%2FC%3A%2FUsers%2F<you>%2F.claude%2Ftoday-board%2Fboard.html`）。
  トークンと申告をヘッダではなくクエリで送るのは、独自ヘッダを付けるとブラウザが送信前に
  OPTIONS の確認（プリフライト）を挟むようになり、要求の形が変わるため
- **照合**: Deck は申告の `file:` URL をローカルパスに直し、自分の board.html と比べる。
  まず I/O の無い `abspath` と `splitdrive` でドライブ部分を比べ、**同じドライブ文字（`C:` 等）の
  ときだけ** `realpath` + `normcase` で正規化して比べる（多重起動ガードのロックと同じ正規化。
  Windows では大文字小文字と `/` `\` の違いを無視する）。**UNC（`\\server\share`）・
  デバイスパス（`\\.\pipe` 等）・別ドライブ・相対パスは照合せず、`realpath` を呼ばずに不一致にする**
  ——申告されたパスをそのまま `realpath` に渡すと、UNC では名前解決・SMB 接続まで進むため
  （Reviewer の実測: 存在しないホストで約 1.25 秒）。ホスト名付きの `file:` URL
  （`file://server/...`・`file://./pipe/...`）も読まない。そのため **board.html 自体を UNC 上に
  置いた構成では、どの申告とも一致しない**
- **Host**: `Host` ヘッダが `127.0.0.1:<自分のポート>`（board.js が使う表記）でない要求は、
  どの経路でも 403 `"host not allowed"`。`localhost:<ポート>` も断る——board.js は使わず、
  許す表記を 1 つに絞れば判定が単純になるため。ブラウザの DNS リバインディング（外部の名前を
  127.0.0.1 に向け直す攻撃）では、ページと Deck が同じオリジン扱いになって GET に `Origin` が
  付かないが、`Host` には外部の名前が残るので、ここで断れる（HTTP の仕様による・未実測）
- **Origin**: `Origin` ヘッダがあって値が `null` 以外の要求は、どの経路でも（`OPTIONS` の
  プリフライトを含む）403 `"origin not allowed"`。file:// で開いたボードは `Origin: null` を
  送る（`[実測]` 2026-10-23・ヘッドレスの Chrome 155.0.8059.86 と Edge 155.0.4283.62。受信側の記録を確かめたのは Chrome 2 回・Edge 1 回。
  GET・POST とも `Origin='null'`・`Host='127.0.0.1:<ポート>'` で、OPTIONS は送られなかった。同じ 2 つのブラウザで、Host・Origin を確かめる v2.1 の Deck が自分のボードの要求を受け付けたことも確かめた〔Chrome＝通知の取得と、設定・時刻上書きの送信／Edge＝設定の送信。各 1 回。D&D の送信は実ブラウザでは試していない〕）。
  この検査が断るのは、**外部のサイトが自分のオリジンのまま送る要求だけ**である（確かめたのは
  `Origin` ヘッダを合成した要求〔`https://example.com` 等〕を断ることで、実ブラウザで外部の
  サイトのオリジンのまま送った要求は試していない）。sandbox 属性付きの iframe など、オリジンが
  不透明なページも `Origin: null` を送り、この検査を通る（Reviewer の実測: トークン導入前の
  v2.1 に、公開サイトを模したページの sandbox iframe から読み書きとも通った）。それを止めるのは
  上の「トークン」である（実測は同項の③）。
  **`Origin` が無い要求は通す**——ブラウザは CORS の要求と GET 以外の要求に `Origin` を付けるので、
  ブラウザから `Origin` 無しで届くのは副作用の無い GET の一部に限られ（その応答はページから
  読めない）、ブラウザ以外のプロセス（curl 等）は `Origin` を自由に偽れるので、求めても守りに
  ならないため（ブラウザの付け方は Fetch の仕様による・本ファイルでは Chrome と Edge の上記
  2 形しか確かめていない）
- **失敗の扱い**: 検査は Host → Origin → トークン → 申告の順で、最初に外れたところで 403 を返す。
  Host・Origin はすべての経路（`/ping`・`OPTIONS`・未知の経路を含む）にかける。トークンと申告は
  `/ping`・`OPTIONS` 以外の既知の経路にかける（未知の経路はその前に 404）。トークンを申告より
  先に見るのは、トークンを知らない相手に、当てたパスが合っているかを教えないため:
  - トークンが無い → 403 `{"ok":false,"error":"token required"}`／違う → `"token mismatch"`
  - `?board=` が無い → 403 `"board required"`
  - `file:` URL として読めない（`http:` 等）→ 403 `"board unreadable"`
  - このボードではない → 403 `"board mismatch"`
  - **書き込み（POST）も読み取り（GET）も断る**。読み取りも断るのは、`/notifications`・
    `/sound/config`・`/board/times` が別ユーザーのタスク名・時刻・設定を返してしまうため。
    断った要求は `sound.json`・board.html に何も書かない
  - 断った記録は `watcher.log` に「受信を拒否: GET /notifications → 403 board mismatch
    （直近 N 件）」の形で、**60 秒に 1 行**へまとめて出る（件数と、最後に断った要求の理由。
    申告されたパス・トークン・Host・Origin の値は書かない）。古いトークンのまま開いているページは
    3 秒ごとに要求を出すため、まとめないとログが埋まる
- **board.js がポートを知る方法**: 上の「トークン」の接続情報（`data-port`）を読む。
  Deck を再起動してポートが替わった場合も、Deck が新しい接続情報を書き、board.js は上記の
  読み直しで追従する。「稼働」と描くのは、`/notifications` が 200 と目印
  `"deck":"today-board"` を返したときだけ
- **ポートが取れないとき**（10 個すべて使用中）: 受信サーバ無しで常駐を続ける。
  **使えなくなるもの**＝D&D 移動の HTML 正本への反映（localStorage 保存に戻る）・⚙パネルの
  通知音設定と試聴・✎ の時刻上書きの中継・未確認通知の受け渡し（リロードで消えない
  ポップアップ）。**動き続けるもの**＝全セッションのカードの自動収集・完了表示の整合・
  時刻トリガーの通知音（`sound.json` に保存済みの設定で鳴る）。接続情報が書かれないので、
  ボードの「監視ねこ」には「不明」と出て、Deck が止まっているか受信ポートを取れずに動いているかの
  どちらかであることを示す（2026-10-26 の修正より前の版の board.js では「停止」と出た。実際には常駐している）
- **限界**: 申告（ボードのパス）は自己申告で推測しやすく、守りの中心はトークンである。
  トークンは board.html に平文で入るので、board.html を読めるもの——同じ Windows ユーザーの
  プロセス、管理者、board.html を読み込む Claude のセッション（today-board スキルは board.html を
  Read で読むことを許しており、読めばその内容は会話の記録と Claude の API に渡る）、artifact モードで
  発行したボード、利用者が人に渡した board.html——はトークンを知りうる。Deck を再起動すれば
  替わる。外部のサイト（sandbox iframe を含む）と別の Windows ユーザーについては、board.html を
  読めないことに依っている（ブラウザ・OS の権限による。別ユーザーでは未検証）。また v2.1 の Deck は `SO_REUSEADDR` を使わずにバインドするが、
  `SO_EXCLUSIVEADDRUSE` も使っていない。そのため、後から起動したプロセスが `SO_REUSEADDR` 付きで
  同じポートに重ねてバインドできるかどうかは確かめていない（未検証）

## 「監視ねこ」セクション

マーカー間の先頭（v2.1 では、画面に出ない接続情報の `span` の次）に「監視ねこ」という見出しを出す。ここには次の 2 種類の行が並ぶ。

- **Deck 自身の生死**（board.js が描画）— Deck は自分が止まったことを board.html に
  書けないため、ブラウザ側が 3 秒ごとの通信の成否から判定して行を差し込む。
  「稼働」と出すのは**このボードの Deck**が 200 と目印を返したときだけ（v2.1）。そうでないときは
  理由で分ける（2026-10-26 の修正以後の board.js。それより前の版ではすべて「停止」だった）: 応答が無い＝「停止」／
  接続情報が無い＝「不明」（Deck が止まっているか、受信ポートを取れずに動いているか、DECK:AUTO の目印が欠けている〔片方だけ・順序が逆を含む〕。
  board.js は目印の間の接続情報だけを読む・2026-10-29）／
  403 `"board mismatch"`・`"board unreadable"`＝「写し」（トークンは通っている＝Deck は動いているが、
  このページは Deck が見ている board.html ではない）／403 `"token mismatch"`＝「古い」（Deck を
  再起動した直後なら読み直しで戻る。同じトークンのまま 2 回読み直しても変わらなければ、Deck の再起動に合わせた読み直しは止める（5分ごとの再読み込みは続く）。
  今日のボードでない板では Deck の再起動に合わせた読み直しはしないので、その旨を出す）／
  それ以外の応答（目印の無い 200〔JSON として読めないものを含む〕・ほかの 403 など）＝「不明」。
  なお CORS ヘッダ（`Access-Control-Allow-Origin`）の無い応答は、ブラウザが fetch 自体を失敗させるので
  「停止」になる（Deck 以外のものが受信ポートで応答している場合を含む）。
  **この見出しが無いと生死行が描かれない**ので、見出しは監視対象が 0 でも必ず出す
- **外部の常駐ツールの生死**（任意連携・既定は無し）— `~/.claude/log-guard/status.txt`
  が存在する場合のみ、その内容（`last` / `state` / `mirror` / `archives`）を読んで
  1 行表示する。ファイルが無ければ何も表示しない。読み取り専用で、Deck 側からは書かない

## ログ・状態ファイル

いずれも `deck_watcher.py` と同じフォルダに作られる（多重起動ガードのロックだけは例外で、
board.html ごとに `%TEMP%\today-board-deck-locks\` に作られる＝上記「起動」・v1.9）。

- `watcher.log` — 起動・再生成・警告を追記。1MB 超なら切り詰め（起動時だけでなく
  **各書き込み時**にチェックする＝長期常駐でも 1MB を超えて成長しない）
- `state.json` — ファイルごとの読了オフセットと畳み込み済みタスク状態。
  削除しても壊れない（次回に全量再パースするだけ）
- `sound.json` — 通知音の設定・発火済み記録・未確認通知・時刻上書き（v1.7）。
  削除しても壊れない。Deck を止めて削除すると、次の起動で通知音の設定は既定（OFF・標準）に戻る（ブラウザには控えが無く、再送されない）。動いている Deck は設定をメモリに持ち、次に保存するときにその値で書き直すので、動いている間に削除しても設定は戻らない（コードを読んで確かめた範囲）。
  `--board` で既定以外のボードを指したときは、ボードと同じフォルダに置く（v2.7）
- `%TEMP%\today-board-deck-locks\deck-<16桁>.lock` — 多重起動ガード用のロックファイル（v1.9）。
  Windows では先頭 1 バイトがロック領域（POSIX の `flock` はファイル全体）で、その後ろに
  保持者情報（PID・board・スクリプト位置・ログ位置・起動時刻）が JSON 1 行で入る。
  **Deck が止まっているときに削除しても壊れない**（次の起動で作り直す）。**稼働中は削除しない
  こと**——Windows では削除自体が失敗し、POSIX では削除するとガードが無効化されて 2 本目が
  起動できてしまう。`uninstall.bat` はこのファイルを消さない（`%TEMP%` に残るが無害）
- `deck/deck.lock` — v1.8 以前のロックファイル。v1.9 は使わない（残っていても無害）

## テスト用オプション

ユーザーデータに触れずに動作検証するためのパス差し替え。通常運用では使わない。

```
python deck_watcher.py --once --projects-dir <dir> --board <file> --state <file>
python deck_watcher.py --rollover-once --board <file> [--today YYYY-MM-DD] [--skill-assets <dir>]
```

`--rollover-once` は日付の切り替えを1回だけ試して終わる（v2.2。同じボードを見る常駐が動いていれば試さない）。
`--today` は「今日」を差し替える（`--rollover-once` と一緒のときだけ受け付ける）。`--board` で既定以外のボードを
指したときは、`--skill-assets` を渡さない限り、本番スキルの静的ファイルを写さない（v2.3）。`config.json`・`state.json`・
`history/` は `--board` のボードと同じフォルダのものを使うので、試験用のフォルダに写して使う。`sound.json` も
`--board` で既定以外のボードを指したときはボードと同じフォルダに置く（v2.7）。`--state` の既定（読了位置の `state.json`）と
`watcher.log` はスクリプトと同じフォルダのままなので、`--state` を渡し、スクリプトは試験用のフォルダへ写して起動する。

## 既知の制限

- `--board` で既定以外のボードを常駐で見ていた場合、v2.6 までの設定（スクリプトと同じフォルダの `sound.json`）は v2.7 のボードの隣の `sound.json` へ引き継がない
- 通知音の設定は Deck の `sound.json` が正で、以前の版の board.js がブラウザに残した値（`tb:sound`・`tb:soundType`）は引き継がない（読み込みのときに消す）
- 発行済みの板の⚙の説明文は、「設定はこのブラウザに保存されます。」の文があれば、board.js が表示のときにその文だけを今の保存先の文へ置き換える。ほかの文は発行したときのままで、HTML の正本も `create` で発行し直すまで古いまま
- 別のブラウザが通知音の設定を変えても、開いているページの⚙の表示は、次の読み込みか、⚙を開いたときか、操作したときまで前の値のまま（操作は送る直前に読み直すので、古い表示で上書きはしない）
- ✎ の時刻の上書きをしたブラウザの記録が消えると（localStorage を消した等）、Deck はその日の終わりまで上書き後の時刻で鳴らし、画面は元の時刻を表示する（コードを読んで確かめた範囲）
- 形が崩れたときの退避（v2.4）は、Deck が動いている間に崩れたときだけ。Deck が止まっている間に崩れた板、
  起動した時点で既に崩れていた板では、崩れる前の版を持っていないので退避しない。日付の切り替えで退避した前の日の
  ボード（`history/board-<日付>.html`）は残る
- 日付の切り替え（v2.2）は local モードで Deck が動いているときだけ。Deck が止まっている間・artifact モード・
  Deck を入れていない環境（macOS 等）では切り替わらず、画面の知らせ（「書き込み停止中」）と次の create に頼る。
  macOS で手で動かした Deck での切り替えは試していない
